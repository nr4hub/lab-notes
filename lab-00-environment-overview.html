Overview & goals

A home lab is a small, safe copy of a company network. You build it once, then reuse it in every lab to attack, defend and investigate without risking real systems. This page documents that environment so each lab guide can say "start the VMs listed in the plan" instead of repeating setup.

Isolated
Attacks never leave the lab network
Repeatable
Snapshots let you reset in seconds
Lightweight
Fits a 16 GB laptop
Documented
Every change is written down
What this page gives you
Lab 00 deliverables
  • A diagram and inventory of every VM in the SOC lab, and which VMs are not part of it.
  • A fixed IP plan for SOC-Lab-Net so addresses never clash.
  • A RAM and disk budget for each of the six labs.
  • Naming rules for snapshots and folders.
  • A pre-flight checklist and a verification script you run before starting any lab.
  • Safety and publishing rules, so nothing risky or private reaches your website.

Lab architecture

All lab VMs sit on one isolated virtual network called SOC-Lab-Net. The pfSense firewall is the gateway between that network and the internet. Lab 01 is the exception: it runs without pfSense, using fixed addresses.

The Windows host sits outside this diagram. It reaches the Wazuh dashboard only through a VirtualBox port-forward (host 127.0.0.1:8443), so the dashboard is never exposed to your home network.

The static addresses .10, .20 and .30 sit outside the DHCP pool (.100–.199), so pfSense can never hand out an address that is already in use.
Network design rules
  1. Attack and monitored VMs use Internal Network only (name exactly SOC-Lab-Net, case-sensitive). They cannot see the host, your home network, or each other's NAT.
  2. Internet access is a separate NAT adapter, used for downloading installers and updates. Never use a bridged adapter on a lab VM.
  3. Adapter type is Intel PRO/1000 MT Desktop on every VM, matching your existing setup.
  4. Only the Wazuh dashboard is reachable from the host, through the 8443 → 443 port-forward on the Wazuh-Server's NAT adapter, bound to 127.0.0.1.
Connectivity test (from Kali-Attacker)

Run this after Lab 01 to confirm the whole network answers. Skip the first line if pfSense is powered off.

ping -c 2 192.168.1.1     # pfSense (skip if powered off)
ping -c 2 192.168.1.20    # Wazuh-Server
ping -c 2 192.168.1.30    # Win-Victim

Expected: replies from every address that is powered on. If one fails, check that both adapters use the exact network name SOC-Lab-Net.

Snapshots, names & folders

A snapshot freezes a VM's disk and state so you can return to it. They are your undo button for failed installs and for attack labs that change the system.

Snapshot naming

Use NN-Short-Description, where NN counts up per VM: 01-Clean-Base, 02-SOC-Net-Verified, 03-Wazuh-Agent-Installed. Keep names short, without spaces, and take one before every risky step.

  • Before any lab: a clean baseline snapshot already exists for each VM you will use.
  • Before installs or config changes: shut the VM down, snapshot, then change.
  • After a working milestone: snapshot again, for example 02-Wazuh-Installed.
  • Prune: delete old, unneeded snapshots occasionally; each one keeps its changed data on disk. In VirtualBox, deleting a snapshot merges it and is safe, but needs free space while it runs.
How to take, restore and delete a snapshot
  1. Shut the VM down first. A snapshot of a powered-off VM stores only the disk and stays small. A snapshot of a running VM also saves its memory (about 4 GB for a 4 GB VM). Linux: sudo poweroff. Windows: Start → Power → Shut down.
  2. Take it. In the VirtualBox Manager window, click the VM, open its Snapshots view (toolbar), then click Take. Type the exact name and click OK.
  3. Restore (undo). With the VM shut down, open Snapshots, select the snapshot and click Restore. This discards everything done after that snapshot. VirtualBox offers to save the current state first; untick that unless you want to keep it.
  4. Delete a snapshot you no longer need: select it and click Delete. It is safe, but needs free disk space while it merges.

The same from PowerShell (run $vbm = ... from the verification step first):

$vbm = "C:\Program Files\Oracle\VirtualBox\VBoxManage.exe"

& $vbm snapshot "Wazuh-Server" take "01-Ubuntu-Base"       # take (VM powered off)
& $vbm snapshot "Wazuh-Server" list                         # list snapshots
& $vbm snapshot "Wazuh-Server" restore "01-Ubuntu-Base"    # restore (VM powered off)
& $vbm snapshot "Wazuh-Server" delete "01-Ubuntu-Base"     # delete

Pre-flight checklist

Run through this once now, and again before any lab where something has changed.

  • Windows 11 is installed and boots on Win-Victim. Note the username you set; the Lab 01 agent steps need an administrator account.
  • Every VM starts from its new location after the move to C: (start each once and shut it down).
  • Adapters match the plan: lab VMs use Internal Network named SOC-Lab-Net exactly; the Win-Victim graphics controller is VBoxSVGA.
  • pfSense default admin password has been changed. It starts with a known default; change it before you rely on the firewall.
  • A clean snapshot exists for pfSense-FW, Kali-Attacker, Ubuntu-Server-Lab and Win-Victim (see the baseline table in Section 6), and you know how to take and restore one.
  • Free space: D: at least 25 GB free before Lab 01 (the new VM needs 12–15 GB), C: at least 20 GB.
  • Laptop on charger with the High performance power plan, and CPU virtualization (VT-x) enabled in the BIOS.
  • Passwords for every VM and the Wazuh admin account are stored in a password manager, not in a text file next to the VMs.
  • Downloaded: Ubuntu Server 24.04 LTS ISO for Lab 01. Keep ISOs in one folder.
Verification commands (Windows PowerShell)

VBoxManage ships with VirtualBox. These list your VMs, their snapshots, and which network each adapter uses:

$vbm = "C:\Program Files\Oracle\VirtualBox\VBoxManage.exe"

& $vbm list vms                        # all registered VMs
& $vbm list runningvms                 # VMs currently on
& $vbm snapshot "Win-Victim" list      # snapshots of one VM

# which network each adapter uses
& $vbm showvminfo "Kali-Attacker" --machinereadable | Select-String '^(nic|intnet)[0-9]'

In the adapter output, nic1="intnet" with intnet1="SOC-Lab-Net" confirms an adapter is on the lab network.

Safety & publishing rules

Safety rules
  • Run attack tools only against your own lab VMs on SOC-Lab-Net.
  • Never attach an attack VM to a bridged adapter or your home Wi-Fi network.
  • Use malware only as harmless test files (EICAR, Atomic Red Team) in the isolated lab.
  • Snapshot before every attack lab and restore afterwards.
  • Disable shared clipboard and shared folders on any VM that handles suspicious files.
Publishing rules
  • Publish: detection rules, configs without secrets, architecture diagrams, screenshots, write-ups.
  • Never publish: passwords, API keys, wazuh-passwords.txt, agent keys, malware, attack scripts.
  • Blur or crop screenshots that show your name, email, device ID or product ID.
  • Credit a tutorial video in one line if you followed it; describe what you added beyond it.
Treat the lab like a real incident environment: the habit of isolating, snapshotting and sanitising what you share is part of what employers want to see.

10

Interview & Cert Takeaways

Be able to explain your lab design out loud in two minutes. These are the points interviewers ask about.

  • Why isolate? An internal network keeps attacks and malware samples from reaching your home network or the internet.
  • VirtualBox network modes: NAT = VM reaches the internet, nothing reaches it. Internal = VMs with the same network name talk only to each other. Host-only = VMs and the host, no internet. Bridged = VM sits on the real LAN (avoid for lab VMs).
  • /24 = 255.255.255.0 = 254 usable host addresses; 192.168.0.0/16 is private (RFC 1918) address space.
  • Static vs DHCP: servers and key lab hosts use fixed addresses; clients can use DHCP. Keep static addresses outside the DHCP pool.
  • Segmentation limits the blast radius: a compromised host can only reach what the firewall lets it reach.
  • Snapshots make labs repeatable, but they are not backups — they live on the same disk as the VM.
  • Baseline first: you need to know what normal looks like before you can call something an anomaly.

අනෙකුත්: Segmentation මගින් බිඳවැටීමක බලපෑම (blast radius) සීමා කරයි. Snapshots lab නැවත කළ හැකි කරයි, නමුත් backup නොවේ — VM එකේම තැටියේ ඇත. Baseline පළමුව: සාමාන්‍ය තත්ත්වය දැන සිටියොත් පමණක් anomaly හඳුනාගත හැක.

Cloud Security Engineer — Real-World Relevance

The same design ideas appear in cloud networks with different names.

VPVirtual network equivalents

SOC-Lab-Net behaves like a private subnet in a VPC, pfSense plays the role of a gateway plus security group, and the NAT adapter resembles a NAT gateway.

Writing your topology, IP plan and rules down is the first step towards infrastructure as code, which you will use for the AWS projects.

Binding the dashboard to 127.0.0.1 and avoiding bridged adapters is the same principle as not opening a cloud service to 0.0.0.0/0.

ලිපිනකරණය: DHCP — පරාසයකින් IP ලිපින ස්වයංක්‍රීයව ලබා දෙයි. CIDR — /24 වැනි සටහන, ලිපිනයේ ජාල කොටස සඳහා බිටු ගණන පෙන්වයි. Subnet — ජාලයක කොටසක් (192.168.1.0/24).

අනෙකුත්: Snapshot — සුරකින ලද VM තත්ත්වයක්. Baseline — වෙනස්වීම් හඳුනාගැනීමට භාවිත දන්නා හොඳ යොමු තත්ත්වය. VPC — cloud සපයන්නෙකු තුළ private, හුදකලා ජාලයක්.

Static vs DHCP: Static — ලිපිනය වෙනස් නොවේ, rules සහ ස්ක්‍රීන්ෂොට් වලංගුව පවතී; නමුත් අතින් සැකසිය යුතු අතර DHCP පරාසය මඟහැරිය යුතුය; pfSense, Kali, Wazuh-Server, Win-Victim සඳහා. DHCP — ස්වයංක්‍රීයයි, සැකසීමක් නැත; නමුත් boot අතර ලිපිනය වෙනස් විය හැක; Ubuntu-Server-Lab සහ අමතර VM සඳහා.
