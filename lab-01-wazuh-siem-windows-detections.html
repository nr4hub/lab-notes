Overview & goals

A SIEM (Security Information and Event Management) system collects logs from many machines in one place, runs detection rules over them, and raises alerts. Wazuh is a free, open-source platform that does this and adds endpoint features such as file integrity monitoring. In this lab you build a working single-node Wazuh, connect a Windows 11 endpoint to it, and then do the part most tutorials skip: writing and testing your own rules.

Lab 01 deliverables
  • A working Wazuh single-node server you can open from your Windows host browser.
  • Win-Victim enrolled as an active agent, sending Windows Security logs.
  • Four real attack-style events investigated in the dashboard (failed logons, new user, admin group change, log clearing).
  • File integrity monitoring on a test folder, with added / modified / deleted alerts.
  • Four custom rules in local_rules.xml, each mapped to a MITRE ATT&CK technique and the NIST CSF DETECT function.
  • A finished lab note: setup diagram, screenshots, detections, and what went wrong.
Lab architecture
Every VM sits on the isolated SOC-Lab-Net internal network, so the attack-style activity in this lab never touches your home network. NAT is used only to download installers and updates.

Lab design & requirements

Only two VMs run in this lab. Everything else (pfSense, Kali, the older Ubuntu server, the LinuxPlus VMs) stays powered off to save RAM.

Change from the original plan: your existing Ubuntu-Server-Lab runs Ubuntu 25.04. That release reached end of life in January 2026, so its package repositories are no longer maintained, and Wazuh's installer officially supports Ubuntu only up to 24.04. This lab therefore uses a new VM on Ubuntu Server 24.04 LTS. Keep Ubuntu-Server-Lab as is — you can still use it later as a monitored Linux endpoint.

Resource check before you start
  • RAM: two VMs use 8 GB. Windows and your browser need about 4–5 GB, so close heavy apps. Your laptop has 15.7 GB usable.
  • Disk: keep at least 10 GB free on D: after creating the Wazuh-Server VM. VirtualBox slows down badly on a nearly full drive.
  • Downloads: Ubuntu Server 24.04 LTS ISO (about 3 GB). Check ubuntu.com for the current 24.04.x point release.
  • Snapshots: you will take one before each major step. Rolling back is faster than debugging a broken install.
  • Time: allow 3–4 hours, or split it across two sessions (stop after Step 3).

Step 1 — Create the Wazuh-Server VM

Create a fresh VM in VirtualBox. Doing this by hand (instead of unattended install) keeps the disk layout and user account under your control.

  1. Download the ISO — Ubuntu Server 24.04 LTS (live server, amd64). Save it next to your other ISOs.
  2. New VM — Name Wazuh-Server. Folder: D:\04_Personal_and_System\16_Virtual_Machines\SOC_Lab\Wazuh\Wazuh-Server. Type Linux, version Ubuntu (64-bit). Tick Skip Unattended Installation.
  3. Hardware — Base memory 4096 MB, 2 CPUs, new virtual disk 30 GB, VDI, dynamically allocated (do not tick "Pre-allocate").
  4. Network → Adapter 1 — NAT, adapter type Intel PRO/1000 MT Desktop. Open Port Forwarding and add two rules (Host IP 127.0.0.1, leave Guest IP empty):
    NameProtocolHost portGuest port
    sshTCP222222
    dashboardTCP8443443
  5. Network → Adapter 2 — Enable, attached to Internal Network, name exactly SOC-Lab-Net, adapter type Intel PRO/1000 MT Desktop (same as your other lab VMs).
  6. Storage — attach the Ubuntu Server ISO to the optical drive, then start the VM.

Step 2 — Install Ubuntu & set the network

Install the OS, give the VM a fixed lab address, and confirm it can reach the internet through NAT.

Installer choices that matter
  1. Base: Ubuntu Server (not the minimized option). Leave both network adapters on DHCP for now.
  2. Storage — important: choose "Use an entire disk" and untick "Set up this disk as an LVM group". The default LVM layout can leave the root volume at roughly half of a small disk, and Wazuh needs the space.
  3. Profile: server name wazuh-server, your own username, and a strong password.
  4. SSH: tick Install OpenSSH server. Do not pick any featured snaps.
  5. When it finishes, choose Reboot, then remove the ISO if VirtualBox asks.
Set the static lab IP

Log in at the VM console and find the interface names (expect enp0s3 = NAT and enp0s8 = internal):

ip -br a

Disable cloud-init's network rewriting, then edit the netplan file so only the internal adapter gets a fixed address. Leaving the gateway off enp0s8 keeps NAT as the default route to the internet.

ls /etc/netplan     # use the file name you see here
echo 'network: {config: disabled}' | sudo tee /etc/cloud/cloud.cfg.d/99-disable-network-config.cfg
sudo nano /etc/netplan/50-cloud-init.yaml
network:
  version: 2
  ethernets:
    enp0s3:            # NAT adapter - internet access
      dhcp4: true
    enp0s8:            # SOC-Lab-Net adapter - fixed lab address, no gateway
      dhcp4: false
      addresses:
        - 192.168.1.20/24

Apply and verify:

sudo chmod 600 /etc/netplan/50-cloud-init.yaml
sudo netplan apply
ip -br a
ip route
ping -c 3 ubuntu.com

Expected: enp0s3 has an address like 10.0.2.15, enp0s8 has 192.168.1.20, the default route goes via 10.0.2.2, and the ping to ubuntu.com succeeds.

Update, check the clock, connect over SSH
sudo apt update && sudo apt -y full-upgrade
sudo reboot

# after the reboot:
timedatectl        # look for: System clock synchronized: yes
hostnamectl

From now on use PowerShell on your Windows host to connect, which lets you copy and paste commands:

ssh -p 2222 YOUR_USERNAME@127.0.0.1
Take snapshot 01-Ubuntu-Base now (VM Machine → Take Snapshot). If anything goes wrong in Step 3 you can return here in seconds.

Step 3 — Install Wazuh all-in-one

The Wazuh installation assistant installs the manager, indexer, dashboard and Filebeat on one machine. This lab uses the 4.14 stable line.

Pre-checks
free -h
df -h /
nproc

You want about 4 GB of total memory and at least 15 GB free on /. If the root filesystem is only about 15 GB on your 30 GB disk, the LVM layout was used — see the Troubleshooting section for the one-line fix.

Run the installer
curl -sO https://packages.wazuh.com/4.14/wazuh-install.sh
sudo bash ./wazuh-install.sh -a

It takes roughly 10–20 minutes. When it finishes, the summary prints the dashboard address and the admin password. Copy the password into a password manager right away. To print all generated passwords later:

# run from the folder where you ran the installer
sudo tar -O -xvf wazuh-install-files.tar wazuh-install-files/wazuh-passwords.txt
The installer checks hardware. If it stops with a memory or CPU warning on your 4 GB VM, you can re-run it with -i to ignore the check. Expect slower performance and keep other VMs off.
Verify and open the dashboard
sudo systemctl is-active wazuh-manager wazuh-indexer wazuh-dashboard filebeat

All four should print active. Then open https://127.0.0.1:8443 in your Windows browser. The certificate is self-signed, so accept the warning, and log in as admin.

Optional: lighten the load and prevent surprise upgrades
# stop accidental upgrades of Wazuh packages
sudo sed -i 's/^deb/#deb/' /etc/apt/sources.list.d/wazuh.list

# optional: cap indexer memory (set -Xms1g and -Xmx1g), then restart it

Step 4 — Enroll the Win-Victim agent

The Wazuh agent runs on the Windows machine, reads its event logs and file changes, and ships them to the manager. Keep both VMs powered on for this step.

  1. Snapshot first. Power on Win-Victim, sign in, then take snapshot 02-Pre-Wazuh (your existing 01-Clean-Base stays untouched).
  2. Set a static IP on the adapter attached to SOC-Lab-Net (the first adapter, MAC ending 2863): Settings → Network & internet → Ethernet → IP assignment → Edit → Manual → IPv4. IP 192.168.1.30, subnet mask 255.255.255.0, leave gateway and DNS empty. The NAT adapter keeps providing internet.
  3. Test connectivity from an elevated PowerShell on Win-Victim. Both ports must report TcpTestSucceeded : True: 
    Test-NetConnection 192.168.1.20 -Port 1515
Test-NetConnection 192.168.1.20 -Port 1514
  4. Generate the install command. In the Wazuh dashboard open Agents → Deploy new agent. Pick Windows / MSI, server address 192.168.1.20, agent name Win-Victim. Copy the PowerShell commands it produces — they contain the correct current version.
  5. Run them in elevated PowerShell on Win-Victim. The generated commands look like this (the version number is filled in by the wizard): 
    # the dashboard wizard fills in the real version for <VERSION>
Invoke-WebRequest -Uri https://packages.wazuh.com/4.x/windows/wazuh-agent-<VERSION>-1.msi -OutFile $env:tmp\wazuh-agent.msi
msiexec.exe /i $env:tmp\wazuh-agent.msi /q WAZUH_MANAGER='192.168.1.20' WAZUH_AGENT_NAME='Win-Victim'
NET START WazuhSvc
  6. Confirm. In the dashboard, Agents should list Win-Victim as Active within a minute.

Step 5 — Generate events & investigate

Windows already logs the events below by default, and the Wazuh agent already collects the Security log. You only need to cause the activity. Run these in an elevated PowerShell on Win-Victim. They are harmless in this isolated lab VM.

# 1) Six failed logons for a user that does not exist (event 4625)
1..6 | ForEach-Object { net use \\localhost\IPC$ /user:labfake "BadPass$_" 2>$null }

# 2) Create a local user (4720) and add it to Administrators (4732)
net user labuser "Lab-Pass-2026!x" /add
net localgroup Administrators labuser /add

# 3) Remove the test user again
net localgroup Administrators labuser /delete
net user labuser /delete

# 4) Clear the Security log (1102) - lab VM only, this erases its local audit history
wevtutil cl Security
What each action should produce
ActionWindows event IDATT&CK ideaWhat to look for in Wazuh
Bad logons4625T1110 Brute ForceSeveral "logon failure" alerts; repeated failures may raise a higher-level alert
New local user4720T1136.001 Create Account"User account created" style alert
Added to Administrators4732T1098 Account ManipulationGroup-membership change alert
Security log cleared1102T1070.001 Clear Windows Event Logs"Audit log cleared" alert
Investigate in the dashboard
  1. Open the Threat Hunting (or Discover) view, set the time range to the last 15 minutes, and search: 
    agent.name:Win-Victim AND data.win.system.eventID:(4625 OR 4720 OR 4732 OR 1102)
  2. Add these columns: rule.id, rule.level, rule.description, rule.mitre.id, data.win.system.eventID.
  3. For the failed logons, open one event and read data.win.eventdata.subStatus. 0xC0000064 means the user name does not exist; 0xC000006A means the user exists but the password was wrong.
  4. Write down the actual rule.id and level Wazuh gave each event. You need these IDs in Step 7.

Step 6 — File integrity monitoring

File integrity monitoring (FIM) tells you when files in a watched location are added, changed or deleted. In Wazuh it is called syscheck. This is the feature the beginner video demonstrates — here you will add your own folder.

  1. On Win-Victim create the folder to watch (elevated PowerShell): 
    mkdir C:\LabWatch
  2. Open the agent config as Administrator (for example, right-click Notepad → Run as administrator → open the file below). Make a copy first. 
    Copy-Item "C:\Program Files (x86)\ossec-agent\ossec.conf" "C:\Program Files (x86)\ossec-agent\ossec.conf.bak"
notepad "C:\Program Files (x86)\ossec-agent\ossec.conf"
  3. Find the existing <syscheck> block and add this line inside it: 
    <directories realtime="yes" check_all="yes" report_changes="yes">C:\LabWatch</directories>
  4. Restart the agent so it picks up the new folder (it must exist before the agent starts): 
    Restart-Service -Name WazuhSvc
  5. Trigger the three change types: 
    "hello" | Out-File C:\LabWatch\notes.txt          # added
Start-Sleep 5
Add-Content C:\LabWatch\notes.txt "changed"         # modified
Start-Sleep 5
Remove-Item C:\LabWatch\notes.txt                    # deleted
  6. In the dashboard, open the File Integrity Monitoring view for Win-Victim, or search agent.name:Win-Victim AND syscheck.path:*labwatch*.
Expect three alerts: file added, modified and deleted. Windows stores the path in lower case, so search with lower-case text. Realtime mode shows that something changed; it does not show who changed it. A stronger mode (whodata) adds that and is a good follow-up experiment.

Step 7 — Write custom detection rules

This is the part that turns a tutorial into portfolio work. Wazuh ships thousands of default rules; detection engineering is deciding which behaviours matter to you, raising their severity, tagging them with ATT&CK, and testing that they fire.

Never edit Wazuh's default ruleset — upgrades overwrite it. Put your own rules in /var/ossec/etc/rules/local_rules.xml and use IDs from 100000 upward.
Workflow
  1. Confirm the parent rule IDs from your own alerts in Step 5. The rules below assume 60122 (logon failure), 60154 (Administrators group changed) and 63104 (audit log cleared). If your dashboard shows different IDs, use yours.
  2. Edit the rules file on Wazuh-Server: 
    sudo nano /var/ossec/etc/rules/local_rules.xml
  3. Add your rules inside the file (below the existing content): 
    <group name="local,lab01,windows,">

  <!-- 1. Tuned brute force: 5 failed logons in 2 minutes (T1110) -->
  <rule id="100101" level="10" frequency="5" timeframe="120">
    <if_matched_sid>60122</if_matched_sid>
    <description>Lab01: 5+ Windows logon failures within 2 minutes</description>
    <mitre><id>T1110</id></mitre>
    <group>authentication_failures,</group>
  </rule>

  <!-- 2. Member added to the local Administrators group (T1098) -->
  <rule id="100102" level="12">
    <if_sid>60154</if_sid>
    <description>Lab01: Member added to local Administrators group</description>
    <mitre><id>T1098</id></mitre>
  </rule>

  <!-- 3. Windows Security audit log cleared (T1070.001) -->
  <rule id="100103" level="14">
    <if_sid>63104</if_sid>
    <description>Lab01: Windows Security audit log was cleared</description>
    <mitre><id>T1070.001</id></mitre>
  </rule>

  <!-- 4. Any file change in the watched lab folder (T1565.001) -->
  <rule id="100104" level="10">
    <if_sid>550,553,554</if_sid>
    <field name="file" type="pcre2">(?i)labwatch</field>
    <description>Lab01: File change inside C:\LabWatch</description>
    <mitre><id>T1565.001</id></mitre>
  </rule>

</group>
  4. Check the syntax before restarting. A wrong parent ID shows up here instead of breaking the manager: 
    sudo /var/ossec/bin/wazuh-analysisd -t
  5. Restart and re-trigger the activity from Steps 5 and 6: 
    sudo systemctl restart wazuh-manager
  6. Confirm the new alerts appear with rule.id 100101–100104, the right level, and the ATT&CK tag.

Think like a detection engineer
  • False positives: a real administrator adds users to the Administrators group too. In a real SOC you would allow-list known admin accounts or maintenance windows. Write down how you would tune rule 100102.
  • Thresholds: why 5 failures in 120 seconds? Try 3 and 10 and note the noise level.
  • Severity: clearing the Security log is rarely legitimate, which is why it gets the highest level here.
  • Evasion: an attacker with admin rights could stop the agent. Note what other signal you would watch for.

Interview & Cert Takeaways

Facts to be able to explain out loud after this lab. They also line up with the SIEM and log-analysis topics in entry-level security certifications.

  • Wazuh has three central components: the manager (analyses events with rules), the indexer (stores and searches alerts) and the dashboard (web UI). Agents run on endpoints. Filebeat ships alerts from the manager to the indexer.
  • Agent traffic uses 1514, enrollment uses 1515, the API uses 55000, and the dashboard uses 443.
  • Custom rules live in local_rules.xml with IDs from 100000; default rules are never edited.
  • Rule levels run 0–15. Level 0 produces no alert; higher means more severe.
  • Key Windows events: 4624/4625 logon success/failure, 4720 user created, 4732 member added to a local group, 1102 audit log cleared.
  • Failed-logon sub-status: 0xC0000064 = unknown user, 0xC000006A = wrong password.
  • FIM (syscheck) detects added, modified and deleted files; realtime sees changes immediately, whodata also records who made them.
  • Detection engineering loop: generate event → find parent rule → write rule → test → tune.
13

SOC Analyst — Real-World Relevance

This lab is the daily SOC loop in miniature: alerts arrive, you investigate, and sometimes you improve the rule behind the alert.

T1Tier 1 triage

Reading a burst of 4625 events and deciding whether it is a user typo or password guessing — checking the sub-status, the target account, and how many attempts in what time window.

DEDetection engineering

Writing, testing and tuning rules like 100101–100104, then documenting false positives. This is exactly what the SentinelOps project showcases.

THThreat hunting

Searching indexed events for patterns no rule flagged yet, such as new local accounts created outside business hours.

SOC takeaway: a log-cleared event (1102) or a surprise Administrators change is a classic post-compromise signal — practise reacting to those within minutes, not days.
14

Cloud Security Engineer — Real-World Relevance

Cloud workloads still run operating systems that need monitoring, and the same ideas apply to cloud logs.

☁Same agent pattern in the cloud

A Windows or Linux instance in a cloud account gets the same agent-to-manager model. Network rules (security groups) decide whether agents can reach ports 1514 and 1515.

CTLink to TrailSIEM

Wazuh also has an AWS integration that can ingest CloudTrail logs, which is a useful point of comparison when you build the TrailSIEM (DETECT) project.

HDHardening your own SIEM

Restrict who can reach the dashboard and the API, protect the admin password, and keep the components on matching versions — the SIEM is itself a high-value target.

Cloud takeaway: detection logic (what you alert on, at what severity, mapped to which technique) transfers directly from endpoint logs to CloudTrail and VPC flow logs.
